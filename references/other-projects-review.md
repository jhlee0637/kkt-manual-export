# 유사 프로젝트 검토: kakao-auto, kakao-cli-win

검토일: 2026-10-02. 클론 위치: `references/other-projects/` (얕은 클론, 각 최신 커밋 2026-10-01).
이 문서는 코드를 **읽기만** 하고 정리한 것이다. 두 프로젝트 모두 실행하지 않았다.

우리 프로젝트의 목표: 카카오톡 PC 대화를 수집해 보존하고, 조직 Slack으로 옮긴다. 기능은 최소한으로 가져온다.

---

## 1. 한눈에 비교

| | kakao-auto | kakao-cli-win |
|---|---|---|
| 수집 방식 | 앱의 **Ctrl+S 대화 내보내기** 자동화 → TXT 파싱 | 로컬 암호화 DB(`chatLogs_*.edb`) **복호화** |
| 라이선스 | Apache-2.0 (NOTICE 재현 의무) | MIT |
| 규모 | Python 약 4,400줄 | Python 약 5,500줄 + PowerShell + 웹 UI |
| 창 자동화 필요 | 필요 (방을 순회하며 클릭, 키 입력) | 불필요 (카카오톡 실행 + 키 복구 때만) |
| 백그라운드 | 불가. 화면, 입력 포커스 점유 | 가능. 파일 읽기 + 복호화 |
| 시각 정밀도 | 분 단위 (TXT 한계) | 초 단위 Unix timestamp (`sentAt`) |
| 메시지 ID | 없음. (방, 시각, 보낸이, 순번, 내용) 해시로 자체 생성 | 있음. `PRIMARY KEY(chatId, logId)` |
| 답장·스레드 | 없음 | 있음 (`replyToLogId`, `threadId` 등) |
| **사진** | 로컬에 저장된 파일만 복사 (아래 §2) | **코드 없음.** 첨부 JSON만 원문 보관 (아래 §3) |
| 위험도 | 약관 위반 가능성 (README 명시) | 약관 + 프로세스 메모리에서 키 추출 (아래 §4) |

## 2. kakao-auto

### 구조 (핵심만)
- `collector.py` (1,074줄): 방 순회와 내보내기. 대부분은 "방 목록을 어떻게 안정적으로 순회하나"에 쓰인 코드다 (픽셀 좌표 클릭, 스크롤 보정, 광고 배너 회피 등).
- `db.py`: SQLite 저장과 중복 제거.
- `export_rooms_csv.py`, `consolidate.py`: 방별 CSV, 일별 TXT 출력.
- `media_backup.py`: 사진 백업.
- 나머지(`dashboard`, `graph_export`, `search`, `extract`, `briefing`, `llm`, `backup`, `cryptobox` 등)는 분석, 시각화 부가기능이다. 우리 목적과 무관하다.

### 가져올 만한 것
1. **Ctrl+S 내보내기 절차** (`collector.py` `export_room`, 539~608행). 우리가 직접 시험해 확인한 흐름과 같다.
   - 창 활성화 → `Ctrl+S` → 저장 대화상자(#32770)를 **win32로** 찾음 → 파일명칸에 경로 입력 → Enter → 완료 팝업에서 Enter.
   - UIA는 모달 대화상자에서 멈추므로 win32로 처리한다는 주석이 있다.
   - 파일 인코딩은 `_read_smart`로 자동 판별(utf-8-sig, utf-8, cp949 순).
2. **TXT 파서** (`parse_clip`, 611~649행). 매우 짧다.
   - 메시지 줄: `^\[(.+?)\] \[(오전|오후) (\d{1,2}):(\d{2})\] (.*)$`
   - 날짜 줄: `^(\d{4})년\s*(\d{1,2})월\s*(\d{1,2})일\s*[월화수목금토일]요일`
   - 다음 메시지 줄이 나오기 전까지는 이전 메시지의 여러 줄 본문으로 이어 붙인다.
3. **중복 방지 방식** (`db.py`).
   - 같은 (보낸이, 시각, 내용)이 반복되면 `seq` 순번을 매겨 구분한다. 우리 설계안의 `ordinal`과 같은 생각이다.
   - 해시는 `sha256(room, sender, sent_at, seq, content)`이다.
   - 증분 수집은 매번 전체 내보내기를 받아 해시로 새 것만 삽입하는 방식이다.
4. **오전/오후 → 24시간 변환**과 ISO 정규화 (`normalize_time`). 초는 항상 `:00`으로 채운다. 설계안처럼 `timestamp_precision: minute`를 따로 표시하는 편이 낫다.

### 가져오지 않을 것
- 방 순회(픽셀 좌표 클릭 + 스크롤 보정). 취약하고 업데이트에 깨지기 쉽다. 방이 몇 개 안 되면 불필요하다. (README에도 이 부분 버그 수정 이력이 길다.)
- 대시보드, 그래프, 검색, 금액 추출, LLM 요약 등 분석 기능 전부.
- 자체 SQLite 중심 구조. 우리는 JSONL 원장을 기준으로 한다.

### 사진 처리 (`media_backup.py`) — 우리 시험 결과와 일치
- 카카오톡이 이미 로컬에 둔 파일을 복사할 뿐이다. 대상 폴더는 `문서\카카오톡 받은 파일`, `%LOCALAPPDATA%\Kakao\KakaoTalk`, `%APPDATA%\Kakao\KakaoTalk` 등이다.
- 파일 sha1로 중복을 제거하고, 20KB 미만 이미지는 이모티콘/썸네일로 보고 제외한다.
- **한계가 코드 주석에 명시되어 있다.** 카카오톡 캐시의 받은 이미지는 `.cng`로 **암호화**되어 있어 복사해도 열리지 않는다. 그래서 **사용자가 직접 "저장"한 파일만** 백업된다. "열어보지 않은 미디어는 못 가져온다"고 적혀 있고, 자동 클릭은 불안정해서 넣지 않았다고 한다.
- 우리가 시험한 방식(사진 클릭 → Ctrl+S → 저장)은 이 한계를 우회하는 방법이다. kakao-auto에는 없는 기능이므로 직접 구현해야 한다.
- 파일 이름은 메시지와 연결되지 않는다 (시각 정보 없이 sha1 앞 10자 + 원래 이름).

### 주의
- README가 약관 위반 가능성과 개인정보(PIPA) 책임을 명시한다. 조직에 도입할 때 같은 검토가 필요하다.
- `HANDOFF.md` 기준 알려진 한계: 이미지/파일/이모티콘은 텍스트로만 표기되거나 누락될 수 있다.

## 3. kakao-cli-win

### 파이프라인
```
KakaoTalk 프로세스(실행 중)에서 키 복구   kwin v2recover
chatLogs_*.edb 복호화                      kwin v2sync
  → messages_v2.sqlite (통합 DB)
  → backend/server.py (localhost:8780, 대화방/메시지 조회 API)
  → (선택) SSH로 원격 서버에 미러링
```
코드 규모의 절반 이상(`mirror.py` 1,388줄, `sync-on-login.ps1`, AGENTS.md의 긴 불변식 목록)은 **원격 VPS 미러링과 그 검증**에 쓰였다. 우리와 무관하다.

### 사진 기능: 코드에는 없다
- `kwin/`, `backend/` 전체에서 사진/이미지/미디어 다운로드, 복호화, 저장 코드를 찾지 못했다 (`photo`, `image`, `media`, `thumbnail`, `jpg`, `.cng`, `download` 검색).
- 복호화하는 대상은 대화 DB(`.edb`)뿐이다.
- 메시지 테이블 `messages`에는 아래가 들어간다.

  | 컬럼 | 의미 |
  |---|---|
  | `type` | 메시지 종류 (정수 원본값, 코드에서 이름으로 변환하지 않음) |
  | `message` | 본문 |
  | `attachmentJson` | 첨부 페이로드 **원문 JSON** |
  | `supplementJson` | 보조 페이로드 원문 JSON |
  | `attachmentSrcLogId`, `replyToLogId`, `threadId`, `prevLogId` | 답장/스레드 관계 |

- 따라서 **사진 메시지가 있었다는 사실과 첨부 JSON은 남지만, 이미지 파일은 얻을 수 없다.** 첨부 JSON에 서버 주소나 키가 있을 가능성은 있다. 그러나 이 프로젝트는 그 값을 해석하지도, 내려받지도 않는다. (실제 첨부 JSON 내용은 확인하지 못했다. 테스트는 reply용 `src_logId` 등만 다룬다.)
- 사진 파일은 kakao-auto와 같은 한계(로컬 캐시 암호화 `.cng`)에 부딪힐 가능성이 크다. 이것은 코드로 확인한 것이 아니라 추정이다.

### 가져올 만한 것 (개념)
- **스키마 설계**가 우리 설계안과 잘 맞는다. 메시지 ID(`chatId + logId`), 정확한 초 단위 시각, 답장/스레드 관계, `type`과 첨부 원문 보존이 그대로 들어 있다.
- 방 분류 (`OM`, `OD`, `MultiChat`, `DirectChat`, `PlusChat`, `MemoChat` → 오픈그룹/오픈1:1/일반그룹/일반1:1/채널/나와의채팅) — `AGENTS.md`에 정리되어 있다.
- 증분 상태 마커(`last-sync.json`의 IN_PROGRESS/SUCCESS/FAILED, 원자적 쓰기)와 같은 운영 패턴.

### 주의 (중요)
- 키 복구는 **실행 중인 카카오톡 프로세스의 메모리를 읽는** 방식이다 (`kwin/memkey.py`: `OpenProcess`, `VirtualQueryEx`, `ReadProcessMemory`). 키를 얻으면 같은 계정의 모든 `.edb`를 복호화한다.
- 이는 kakao-auto처럼 앱의 정상 내보내기 기능을 쓰는 것과 성격이 다르다. 약관 위반 가능성은 두 방식 모두 있지만, 이쪽은 **암호화를 푸는 행위**라는 점이 추가된다. 조직(Slack으로 공유) 맥락에서는 법무, 보안 검토가 먼저 필요하다.
- 개인 PC에서 본인 계정만 대상으로 해도, 대화 상대의 정보가 포함된다는 점은 같다.
- 안티바이러스가 메모리 읽기 도구를 악성으로 탐지할 수 있다 (추정).
- 이번 검토에서 이 도구를 **실행하지 않았다**. 도입하려면 위 검토를 먼저 거치고, 테스트 계정으로 시험하기를 권한다.

## 4. 우리 프로젝트에 대한 시사점

1. **텍스트와 시각**
   - kakao-cli-win 방식은 정확하지만 위험도가 다르다.
   - kakao-auto 방식(Ctrl+S → TXT)은 분 단위 시각이다. 사진 메시지만 파일명에서 초/밀리초(`KakaoTalk_20261002_092809534.jpg`)를 얻을 수 있다.
   - 우리 방은 "공식 내보내기 TXT를 원본(raw)으로 보존"하는 쪽이 가장 방어하기 쉽다.
2. **사진**
   - 두 프로젝트 모두 사진 자체를 안정적으로 얻는 방법은 없다.
   - 우리가 시험한 "사진 클릭 → Ctrl+S → 저장 대화상자에 경로 입력"이 현재로서는 유일하게 확인된 방법이다. 화면 점유가 필요하다.
3. **Slack 이전**
   - 두 프로젝트에 Slack 코드는 없다.
   - 메시지는 `events.jsonl` 같은 중간 형식으로 두고, Slack 전송 어댑터를 따로 만드는 구조가 맞다.
4. **kakao-auto에서 직접 참고할 코드 (작은 범위)**
   - `export_room`: Ctrl+S와 저장 대화상자 제어
   - `parse_clip` + `MSG_RE`/`DATE_RE`: TXT 파싱
   - `db.make_hash`/`seq`: 중복 방지 아이디어
   - 이 코드를 그대로 가져오면 Apache-2.0에 따라 NOTICE 등 저작자 표기를 해야 한다. 아이디어만 참고해서 새로 쓰면 그 의무는 없다.
5. **kakao-cli-win에서 참고할 것은 코드가 아니라 스키마**
   - 필드 구성(`logId`, `replyToLogId`, `type`, `attachmentJson`)과 방 분류만 참고한다.

## 5. 확인하지 못한 것
- 두 도구의 실제 동작. 실행하지 않았다.
- `kakao-cli-win`의 첨부 JSON 실제 내용과 `type` 정수값의 의미. 코드에 이름 변환이 없다.
- 카카오톡 PC가 사진을 `.cng`로 두는 것이 모든 버전에서 같은지.
- 약관, 법적 해석. 이 문서는 법률 자문이 아니다.
